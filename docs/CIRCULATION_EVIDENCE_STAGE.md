# 逐件流转独立存证实施记录

更新：2026-10-25。本批继续批次 B，将明确关联的本件出库、运输与逐件收货留档生成独立证据版本。

## 使用路径

在销售出库的“核对包装码 / 逐件收货”或运输详情中，切换到“本笔出库已关联的码”，点击“查看 / 提交流转存证”。预览内容、版本及摘要后，勾选确认再提交。只读账号可以预览，不能提交。

本码须已完成生产来源存证；提交还会实时核对链上批次、单品、来源摘要与可用状态。未关联实际出库、生产证据未冻结或来源未确认时，返回明确提示，不通过旧通用事件入口绕过。

## 版本与恢复规则

- 每版仅冻结公开白名单：出库与关联留档时间、运输状态及事件类型/时间、明确逐件核对的实收/拒收。客户、地址、联系方式、人员、说明和凭证引用不进入本版。
- 摘要同时绑定包装码哈希、原包装来源摘要、生产证据摘要、版本号及前版摘要。生产清单及旧流转清单不覆盖；当前事实没变化时重用原版。
- 运输或逐件结果后补时，先展示新候选版本。旧版未确认时可选择“核对 / 恢复上一冻结版本”，不能跳过未知版本直接发布后版。
- 按订单、包装、运输顺序锁定来源，与销售出库、运输安排及收货共用业务锁，避免冻结时混入一半更新的运输状态。每版使用五分钟处理租约；网络调用前持久化冻结快照、事件及待提交交易，远程写调用不占数据库长事务。
- 先读取链上批次、单品和事件。相同事件已存在且摘要、所属码、类型、时间和索引一致时直接复用。前版须实时核验；结果未知时停止重发，后续读取匹配即可恢复。明确失败回执或 `CHAIN_DISABLED` 可经确认重试。
- 每码最多 50 版，链事件核对上限 200 条。达到版本上限后仍可查看、恢复旧版，新增事实不会被宣称已纳入原版。

复用合约 `appendTraceEvent`，事件类型为 `LOGISTICS`，事件发生时间表示“本版证据留档时间”；真实出库、发运和收货时间保存在快照内，不冒充现场物流。没有修改合约、ABI 或包装码状态。

## 公众核验

生产证据与流转证据分别显示结论。未提交、等待确认、失败或当前业务已有新事实时，不能用旧版成功结论覆盖当前事实。

逐版核对内容摘要及前序关系；最新快照与当前公开事实一致，且本版及所有前版均在本次实时链读取中匹配，才显示“当前流转摘要一致”。可展开各版查看冻结内容、实际时间、本版/前版摘要。节点不可用时保留查询能力，标为尚未实时核验通过。后台收货代录仍不等于消费者身份验证或外部物流认证。

## 接口与部署

- `GET /api/production/items/{id}/circulation-evidence`：只读预览候选版本、冻结版本及回执。
- `POST` 同路径：提交 `expectedManifestHash`，既支持当前预览，也支持恢复最近冻结版本。未冻结的候选资料变化后，旧预览被拒绝；最近已冻结的摘要明确用于恢复原版。
- 公众查询增加 `circulationEvidence`，包含逐版快照、实时核验状态和当前事实是否与最新版一致。

已有环境执行 `database/migrations/013_circulation_evidence.sql`；完整 `database/schema.sql` 已同步。可从仓库根目录用 Java 11、现有 MySQL JDBC 驱动运行 `scripts/ApplyCirculationEvidenceSchema.java`；脚本只新增版本表，从忽略的 `.env` 读取连接，不输出凭据。本机已应用。部署新代码前需升级。
