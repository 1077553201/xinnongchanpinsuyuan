# 原始交易回执核查与留档

更新：2026-10-26。继续证据集中对账，补充按已经保存的原交易哈希读取实际回执；本批没有重发或新增链交易。

## 办理路径

证据对账 → 查链核对 → 原始交易回执 → “只读核对原始交易回执”。查询和留档均先按机构核对原业务来源，只读账号可以查询；留档另需写权限、CSRF 和本次核对摘要。

- 只使用原意图中已保存的交易哈希，不接受客户端手填哈希。没有意图、缺少哈希、哈希不合法、未查到、节点不可读及资料冲突分别显示，均不推造成功或失败回执。
- 成功回执要求交易哈希、目标合约、原提交人、完整调用编码和对应事件均一致。生产批次的产品与开始时间、包装码所属批次、流转/质检事件编号与类型及时间、NFC 绑定和停用原因摘要都绑定原冻结操作。
- 失败回执没有成功事件可作依据，仍须核对完整原调用、目标合约、交易身份和区块。只把这一次原调用记为失败，不推断所有同源业务都失败，也不自动退款、退库或重发。
- 用户确认后，重新读实际回执，在来源与记录锁内再次核对原意图、摘要和处理租约，再保存本地交易核验元数据及审计。已有相同留档不重复保存，读到不同结果则停止覆盖。

## 原记录与时间边界

保留原交易哈希、提交时间、业务编号、请求摘要、目标合约和事件信息；不把另一次匹配的业务事件移接为原交易。回执核验只更新原交易的实际状态、区块、状态码、提交人及核验标记，不改采收、库存、销售、运输、NFC 停用或冻结证据版本。

核验标记阻止迟到的普通提交回调覆盖已核对的回执。此后若确切失败需要再次提交，仍由原业务入口明确确认并创建新的交易意图，不能覆盖原交易历史。业务证据的“确认补记”与原始回执留档仍是两个独立步骤。

页面的“本次核对”“核对留档”为本地时间，不冒充区块产生时间；原 `confirmed_at` 为本地处理时间，已有值不覆盖。实际区块号来自节点回执。当前只信任已配置合约，历史合约地址与当前配置不一致时停止核验，未自动建立历史合约白名单。

## 技术与部署

- SDK 3.0.0 读取原回执并重建完整 ABI 调用；只提取目标合约的预期事件，重复目标事件不通过。对节点返回的十六进制地址、哈希和日志主题统一前缀与大小写，完整内容仍须相同，不放宽归属匹配。
- `GET /api/production/evidence-reconciliation/{kind}/{id}/receipt` 只读查询；`POST` 同路径携带 `expectedCheckHash` 确认留档。返回核验摘要和必要回执字段，不返回原始调用数据、私钥、附件或内部停用原因。
- 部署前应用 `database/migrations/017_receipt_verification.sql`，为 `chain_transaction` 增加 `receipt_verified_at`、`receipt_verification_hash`。完整建库脚本已同步；已有环境可运行 `scripts/ApplyReceiptVerificationSchema.java`，会检查列是否存在。本机已升级，不重置原值，无需部署新合约。

## 验证

- 后端累计 440 项测试、前端 39 项测试及构建通过。覆盖完整 ABI 编码、真实事件日志解码、无前缀节点日志、错误哈希/合约/原调用/提交人、重复或缺失事件、失败回执归属、缺少哈希、机构/角色、确认变化、锁内意图变化和迟到回调保护。
- 真实只读核查既有 11 条 QA 原交易：生产 4、流转 2、质检 3、NFC 2，调用与事件全部一致。联调中定位并修正节点日志无 `0x` 前缀的兼容问题，未通过的中间结果未当作成功。
- 经明确授权，仅为既有 QA NFC 停用交易 #30 保存一次真实回执核验元数据及审计；原哈希与区块保持一致，重复查询显示已留档。原生产、流转、质检和 NFC 操作记录保持不变，未新增链交易。
- 缺哈希、实际失败和并发变化通过隔离自动测试验证，没有把经营记录改坏来制造联调样例。
- 原浏览器测试空间已关闭且没有可恢复窗口；已申请新窗口授权，暂未完成本批原回执面板的桌面/手机交互和截图复核。功能测试及 API 联调不代替本次视觉验收；上一批集中对账截图也不作为本批新增面板的截图证据。

## 后续

本批是人工触发的原回执核查，不代表已具备异步自动对账、无哈希交易发现或全局补偿。后续按计划推进业务更正与拒收/召回异常留档，先厘清原事实、影响数量和证据关系，不自动退回可售库存或生成退款。真实标签、田间设备和完整现场试点仍待验收，设备反馈继续保留原待复核状态。
