## 3. 本次核对纠正的认知

1. 早期 `FRONTEND_PREPARATION.md` 中“小车复用 MQTT、后端零改造”的结论已经过时。新种植模型要求移动巡检独立确定任务与地块，`MonitoringService` 明确拒绝车辆固定绑定。
2. 订阅 `status/event` 不代表任务状态已持久化，不代表已有命令下发、ACK 或实际完成闭环。
3. Topic 的农场/网关字段一致性不等于设备验签；Broker 用户认证也不直接替代采样端身份校验。
4. 旧批次窗口上链、新种植周期窗口、采收后生产证据是不同层次，不能混为生长全过程已实时上链。
5. 阶段文档的“下一步”是历史截面；赋码、质检、NFC、流转和回执等后来已有实现，不能按旧缺口再开发一遍。

## 4. 开发模式与范围冻结

- 以“可复现问题→最小修复→真实链路回归→交付证据”推进，不继续按菜单数量扩功能。
- 优先稳定已具备的地块、环境、农事、采收包装、库存销售、运输和证据查询，不重设计现有主题。
- 检测车纳入首版核心链路，不再沿用旧计划中整车一概后移的排序；自动导航等高级能力不随之全部提级。
- 固件/协议未确定时先补档案与真实消息样本，不先造完整车控平台。
- 软件 QA、实机台架与现场经营分别标注；演练数据不能充当真实生长期证据。
- 每轮围绕一个阻塞项完成检查并本地提交，只有要求时推送。
