## 1. 规划背景与定位调整

项目要建设能够支撑实际经营的农产管理系统，覆盖地块种植、生长监测、农事作业、采收包装、库存销售、运输交付和消费者溯源验证。

目前已经打通的产品、批次、单品码、设备消息和链上核验等能力，是可复用的技术基础，但不代表真实经营流程已经完整。仅添加“采收事件”“销售事件”，不能替代采收称重、库存扣减、订单履约等业务。

后续开发以真实业务闭环为验收依据。业务操作自然产生溯源记录，AI 降低操作成本，区块链保存关键证据摘要，二维码/NFC 提供最终查询入口。

## 2. 本次明确的需求与待细化事项

### 已明确的方向

- 以对生长环境要求严格的农产品作为重点场景，先登记地块，再登记所种产品和品种。
- 为地块上的本轮种植绑定传感器、小车等监测资源，持续记录生长环境并保存链上证据。
- 采收后保留产品来源，衔接包装、销售、运输和消费者收货。
- 地块本轮种植结束后可以种植其他产品，历史记录必须保留。
- 二维码和 NFC 用于成品的最终验证查询。
- 增加业务 Agent，使用户通过自然语言完成操作；支持从长段日报提取多个事项，整理后列出操作，用户确认后执行。

### 待业务细化后确定

- 首个试点的农产品、品种、经营主体和实际地块。
- 散装称重、标准包装或两者并存的销售方式，以及首期配送流程。
- 人员分工、审核要求、监测指标、环境范围和数据采集频率。
- 具体传感器和小车能力、设备定位方式、控制协议及任务回执能力。
- 库存单位换算、分级规则、损耗处理和批次混合规则。
- AI 模型供应方、调用预算、部署方式和数据访问范围。

以下阶段安排和业务规则为建议方案，具体字段、接口和实现方案应在对应阶段细化，不能把未确定事项当作既定需求。

## 3. 生产到交付的业务主线

```text
地块登记 → 开启种植周期 → 绑定监测与农事执行
                            ↓
                       分次采收批次
                            ↓
                  分级包装 → 入库 → 销售出库
                                         ↓
                                  运输 → 交付消费者

种植周期结束 → 释放地块 → 可开启下一轮种植
各环节业务记录 → 来源关联与证据存证 → 二维码/NFC 查询验证
```

| 环节 | 主要业务操作 | 应形成的记录 |
| --- | --- | --- |
| 地块登记 | 登记位置、面积、负责人和识别名称 | 稳定的地块身份与历史 |
| 开始种植 | 选择产品、品种、种植时间及环境要求 | 关联地块的种植档案 |
| 监测与农事 | 安排设备、巡检任务，记录灌溉、施肥等操作 | 环境数据、作业记录、人员及附件 |
| 异常处理 | 识别超限、缺测和设备离线，登记处理措施 | 告警、处置过程与恢复情况 |
| 采收分级 | 登记日期、重量、等级与损耗 | 可核对数量的采收批次 |
| 包装入库 | 建立包装规格、包装批次、赋码和入库 | 库存台账及包装来源关联 |
| 销售运输 | 记录订单、出库、承运和交付 | 数量、去向、责任人及运输记录 |
| 消费者验证 | 扫码或读取 NFC | 来源、生产环境、流通过程与核验结果 |

## 4. 核心业务对象和规则

### 4.1 地块与种植周期分开管理

“收获后注销地块”建议实现为结束本轮种植、释放地块，不删除地块本身。地块长期存在，不同产品、品种和种植时间分别建立种植周期。

种植周期结束前，需要核对未完成作业、后续采收及设备任务。历史种植、环境和产品来源继续可查，不因设备解绑或地块重新使用而改变。

### 4.2 设备归属保留时间范围

设备数据关联设备、采集时间、地块和种植周期，保留绑定与解绑的生效时间。设备转移后，不能按当前绑定关系重新归属历史数据。

小车可能巡检多个地块，应通过巡检任务及采集位置等信息确定数据来源；不能仅根据设备当前所在页面或人工简称判断。无法确定来源的数据应标为待核实，不能直接充当某块地的生长证据。

### 4.3 种植、采收、包装批次分开管理

一轮种植可以分次采收，一次采收可以分级、分装成多个包装批次。销售和配送必须能够追到具体来源。

数量核对覆盖采收、分级、包装、损耗、入库、出库和退货。称重单位与箱、袋等包装单位之间的换算必须有依据，不能由 AI 猜测。首期不明确支持的混批或合批，应限制操作，避免丢失来源关系。

### 4.4 区分事实、计划和执行状态

“明早送货”创建配送计划，不代表已经发货；“准备清棚”不能记录为清棚完成。采收记录、库存流水、订单和运输任务分别有自己的状态及前置条件，溯源时间线读取这些业务结果。

## 5. 环境监测与可信证据

每轮种植需明确监测指标、适宜范围、采集频率和数据完整性要求，并保留所采用规则的版本。指标可涉及温湿度、光照、土壤环境等，实际范围由试点业务确定。

环境管理同时呈现：要求是什么、实际发生了什么、异常如何处理。超限持续时间、缺测、离线和处置记录都应保留；不能只展示“环境合格”。没有配置范围或数据不足时，应明确显示无法判断。

原始数据和业务明细保存在链下，按确定的时间窗口或关键业务节点生成规范化摘要上链。查询时分别展示业务记录、证据来源、上链状态和实际核验结果。上链失败或待处理不能显示为已验证。

区块链帮助核验已存证记录的一致性，不能单独证明现实中的操作确实发生。人工口述、设备实测、附件和审核记录需要分别标明来源。运输环境数据关联运单或货物批次，不能混入种植环境统计。

## 6. 二维码与 NFC 的定位

先形成种植和采收来源，在包装赋码时建立产品查询身份，不要求播种时就创建未来每件成品的单品码。

二维码和 NFC 指向同一产品身份及查询结果。消费者可查看来源地块、产品品种、种植周期、环境摘要、农事、采收、质检及运输交付记录，并了解哪些证据可核验、哪些信息缺失。

标签绑定与链上核验分别显示；普通标签可读取不等于商品必然真实。面向公众的信息应限制在获准公开的业务范围，不暴露人员隐私、客户资料和设备访问凭据。

## 7. AI Agent：核心业务操作入口

### 7.1 角色与能力

Agent 是农业业务助理，与手动页面并存。它读取当前用户有权访问的业务资料，理解自然语言，整理待办操作，用户确认后调用系统业务能力。

首期重点是“日终长文本整理”，之后逐步扩展到业务查询、异常解释、每日复盘和设备任务协调。消费者助手作为后续能力，仅依据允许公开的溯源资料回答问题。

Agent 不直接修改数据库，不自行决定监测阈值，也不把模型生成的内容当作现场证据。库存计算、权限校验和状态流转由业务系统执行。

### 7.2 长文本整理示例

用户输入：

> 今天东边棚的草莓采了八十斤，其中十斤品相一般单独放，剩下的装了七箱。下午湿度太高，老张开了通风。三箱发给李老板，明早送。小车今天换到西边棚巡检，东边棚这季结束了，准备清棚。

Agent 应查询上下文并形成待确认操作单：

| 事项 | 拟处理操作 | 需要核对 |
| --- | --- | --- |
| 采收八十斤 | 登记本轮种植的采收批次 | 地块、种植周期、实际日期和重量单位 |
| 十斤单独放 | 登记分级及存放去向 | 等级和用途 |
| 剩余装七箱 | 建立包装批次并登记入库 | 是否已入库、每箱净重与规格 |
| 湿度异常、开通风 | 关联异常并补充处置记录 | 告警、处置时间及人员身份 |
| 三箱给李老板 | 创建销售及次日配送草稿 | 客户、价格、批次及实际出库状态 |
| 小车换地块 | 调整巡检任务 | 生效时间和是否下发设备指令 |
| 本季结束、准备清棚 | 提议结束种植并安排后续任务 | 是否还有未完成采收或作业 |

示例中的数量仅用于说明交互，不作为系统默认规格。不能根据剩余重量直接断言每箱净重；“今天”的解释应结合用户时区、输入时间并在确认单展示具体日期。

### 7.3 标准交互流程

1. **理解整理：** 提取对象、时间、数量、单位和操作，区分已发生、计划及不确定事项，保留来源文本。
2. **查询核对：** 匹配真实地块、人员、客户和批次；检查库存、设备状态和前置条件。系统能查清的信息不重复追问，重名和歧义需澄清。
3. **生成确认单：** 显示每项操作、关键字段、影响和待补信息，支持逐项修改、排除或只确认部分事项。
4. **绑定确认版本：** 确认对应具体版本和操作范围；内容修改后不得继续执行旧版本。执行前重新校验权限和业务状态，关键条件变化时重新确认。
5. **依赖执行：** 先采收，再分级包装、入库，最后处理销售出库；有未解决前置条件的操作保持待办。
6. **真实回执：** 逐项返回成功、失败和待处理结果，给出业务记录入口；业务保存、上链和设备执行分别报告状态。

### 7.4 执行边界与可靠性

- 手动页面和 Agent 共用业务服务、权限、校验与审计规则。记录提出人、确认人、确认版本和执行结果。
- 重复日报、重复确认和网络重试需要识别重复，避免重复采收、入库、扣库存或下发设备任务。
- 批量操作可能部分成功；回执必须准确，重试仅针对允许重试的失败项，不能整单盲目重做。
- 已确认或已存证的业务记录采用更正流程，保留原始记录及原因，不静默覆盖历史。
- “安排巡检”“下发任务”“设备接收”“实际完成”分别处理；没有设备回执不能声称小车已完成任务。
- 检索到的附件、设备消息和用户文本作为业务数据处理，不能作为提升权限或绕过确认的执行指令。
- 主动提醒与每日复盘可以生成建议；首期不因此自动改变库存、结束种植、出库或控制设备。

## 8. 管理端页面方向

首页围绕当前工作展示：在种地块、环境异常、待处理农事、待采收、待发货和在途货物。产品数量、交易数量和链状态放在辅助位置。

建议业务导航包括：工作台、地块与种植、监测与巡检、农事作业、采收与包装、库存与销售、运输交付、溯源与证据、AI 助理。设备和系统配置作为管理功能，最终菜单随首期范围调整。

AI 对话入口支持随时调出；长文本输入后展示结构化确认单及执行进度，并能打开相应业务页面。传统表单继续支持精确录入和人工处理异常。

## 9. 分阶段推进与验收

| 阶段 | 主要交付 | 验收重点 |
| --- | --- | --- |
| 0：试点与业务蓝图 | 选定实际场景，明确角色、单据、状态、数量规则和 Agent 操作清单 | 能用一组完整业务实例说明每一步由谁操作、留下什么证据 |
| 1：生产与监测基础 | 账号权限、地块、种植周期、设备绑定历史、巡检归属、农事记录 | 换季和设备转移后历史数据归属不变；无权限操作被阻止 |
| 2：采收到交付闭环 | 分次采收、分级包装、库存、销售、运输交付及来源关联 | 来源可追、去向可查、数量与损耗可核对 |
| 3：Agent 首版 | 长文本整理、业务匹配、追问、版本确认、批量执行和回执 | 用户确认后准确落账；歧义、重复和部分失败不造成错误业务 |
| 4：证据整合与实地验收 | 将新业务接入现有存证和扫码入口，补充查询复盘与异常解释 | 消费者能核验真实批次的生产和运输记录，缺测与失败如实显示 |
| 5：扩展能力 | 真实小车任务联动、更多销售场景和消费者助手 | 按实际硬件及试点需要独立验收 |

Agent 的操作接口与确认机制从阶段 0 同步设计，随业务接口成熟逐步接入；不等所有页面完成才设计 AI。现有链上核验在前期继续复用，阶段 4 集中验收完整业务证据。

完整试点至少覆盖：同一地块分次采收、不同包装去向、一次环境异常及处置、设备转移、种植换季、库存出库与交付，以及一段真实日报的 Agent 确认执行。若首期包含退货，也须验证数量和来源回溯。

测试通过、模拟消息接入和实地验证分别报告。硬件巡检、现场采集、实际标签及真实配送不能用页面截图或模拟数据代替验收。

## 10. 现有工程的复用与调整

- 继续复用 Vue、Java、MySQL、MQTT 和 FISCO BCOS 基础，以及现有设备接入、二维码/NFC 和真实链上核验能力。
- 重点调整业务数据模型、状态、权限、服务接口和页面工作流，不靠扩充通用事件类型替代业务建模。
- 现有通用批次和事件与新业务对象的映射需制定迁移方案；历史记录不能凭空补齐来源。测试数据与真实经营数据应明确区分。
- 后续每次开发按确认的阶段推进，记录本阶段范围、验证证据和未解决问题。农业操作控制和业务落账均使用确定的服务能力。
- 不默认扩展为完整财务、采购或电商平台；这些范围是否需要，由试点业务另行确定。
