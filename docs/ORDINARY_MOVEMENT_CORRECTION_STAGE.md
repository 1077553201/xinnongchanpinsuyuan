# 普通入出库数量更正

实施日期：2026-10-26。对应 `NEXT-07` 普通库存单据首批；销售履约、运输收货与退货放行更正仍未完成。

## 入口与允许范围

在“库存台账 → 按种植来源查看 → 具体包装 → 原始流水”点击“更正数量 / 查看调整历史”。损耗仍走原损耗调整规则；入库和出库打开普通数量更正面板。

本轮仅允许**同仓、同包装最近一张普通 IN/OUT 单据**的数量录错调整。原始件数、重量、人员、时间和原因不改写，追加独立版本。填写核实后的该单总件数（不是差额），支持归零和后续版本修正，单据仍最多 100 版。

以下任一情形禁止普通更正，预览列出阻止原因：

- 同仓同包装已有后续原始流水；即使后续单据已调整为零，也保留其依赖事实。
- 本单已关联销售出库。
- 同包装来源已有销售订单明细，包括已完成、取消或停止的历史订单。
- 同包装来源已有关联具体包装码的逐件出库。

关联规则按整个包装来源检查销售依赖，不只看当前仓。冻结的生产、流转、质检记录可在预览中核对，数量调整不改写这些记录，也不自动产生新链交易。本轮未将普通仓储数量加入公众存证事实，不能把调整单视为已经上链或质量验收。

## 数量、并发与历史

入库更正的库存差额为“新件数 − 当前有效件数”，同时调整有效累计入库；普通出库为“当前有效件数 − 新件数”，累计入库不变。不得导致本仓或本来源余额为负、累计入库超出实际包装件数、余额超过有效入库。

例如入库原单 5 盒核实为 3 盒，当前余额与有效累计入库各减 2；后续再核实为 5 时增加下一版，不覆盖原单或前版。原普通出库 2 盒核实为 1，当前余额增加 1；须核实实物仍在普通库存，不能用此入口放行隔离退回货物或代替盘盈。

沿用影响快照、原单摘要、前序摘要、核实人员/时间、登记账号与幂等确认标识。预览与保存分别校验；被阻止的预览无人工同意勾选，确认按钮禁用，直接调用提交接口同样被拒。

普通流水、销售出库、更正共用包装行锁；新建销售订单也按包装 ID 升序取得相同锁，避免新销售依赖与确认更正同时提交。已有成功请求在后来出现下游后仍可按原标识查询重放结果，不再写入；新调整则重新接受依赖校验。

损耗与普通入出库共享校验实现，但分别存储，原损耗 V1 摘要和三版 QA 历史兼容不变。各来源/分仓/仓库库存统一通过当前有效流水视图计算，原始流水与调整历史分别展示。调整作用于当前余额，不倒改历史单据，不提供任意历史时点库存报表。

## 部署

先完成此前迁移，部署前执行 `database/migrations/020_inventory_quantity_correction.sql`，或在仓库根目录用 Java 11 与 MySQL JDBC 驱动运行 `scripts/ApplyMovementCorrectionSchema.java`。脚本从忽略的 `.env` 读取配置，新增普通数量调整表并更新当前库存视图，保留原损耗表和原流水；新库 `database/schema.sql` 已同步。

迁移后须保留最新视图定义，不单独回退旧库存代码，也不要单独重跑第十九批脚本覆盖视图，否则普通入出库调整将被遗漏。无需重部署合约。

- 明确授权的 QA-MOVE：复用测试周期 #28，新建采收 #18、分级 #18、包装 #224（5 盒 × 1 kg）及仓库 #16。入库 #243 更正 5→3→5，普通出库 #244 更正 2→1→0；库存序列 **5→3→5→3→4→5**。每次相同确认重试不重复写入，最终新仓库 5 盒。
- 新出库后原入库无法再普通调整；旧仓库、原损耗及拒收处置保持不变。未赋码、未发送链交易。以上为软件构造测试留档，不代表现场采收或真实货物盘点。
- 浏览器查看原单与两版出库调整历史，生成下一版只读预览而未提交；1440/768/390/320 像素宽度下弹窗处于视口内且无横向溢出。截图请求超时，像素视觉验收未完成。运行输出与浏览器产物保持忽略，软件检查不替代实地验收。
