更新时间：2026-10-21。承接 [生产到销售及 Agent 规划](PRODUCTION_TO_SALES_AGENT_PLAN.md) 阶段 2，先建立可核对来源与重量的采收、分级和包装记录；库存、销售与运输随后接入。

后续进度：库存基础已在下一批接入，见 [库存台账阶段记录](INVENTORY_LEDGER_STAGE.md)。本文件保留采收阶段的实现和验收边界。

## 使用流程

登录后进入“采收与包装”（`/admin/harvest`），选择具体种植周期；地块档案也提供入口。

1. **登记实际采收：** 每次采收独立建立批次，填写实际时间、扣除容器后的净重、单位、现场人员和说明。保留来源周期、原录入数量与单位，以及登录录入人和录入时间。
2. **登记分级与损耗：** 同一采收可以分为多个可用等级，填写重量、实际时间、人员和存放位置；损耗单独登记名称、重量与原因，不作为可包装来源。系统不提供默认等级或质量结论。
3. **完成分级核对：** 必须满足“可用等级重量 + 损耗 = 本次采收净重”，才可确认完成；有差额时保持待核对。确认后不可追加分级或覆盖原记录。
4. **登记实际包装：** 选择一个可用等级，填写实际件数、包装单位、单件净重、办理时间、人员和位置。每批只允许一个来源，不支持混批。未包装部分保留余量，可分次包装。

例如软件联调用 80 市斤建立 40.000 kg 采收，分出 35.000 kg 可用果与 5.000 kg 损耗；可用果最多记录 7 箱、每箱 5.000 kg 的包装。这是数量校验示例，不是实际生产或规格建议。

## 数量、权限与历史

- 采收单位支持公斤、克、市斤；1 市斤明确为 500 克。保存统一公斤净重，精度 1 克，使用十进制定点数；不能精确换算到克的输入直接拒绝，不静默舍入。
- 分级与损耗合计不能超过采收净重，包装净重等于件数乘实际单件净重，累计不得超过该等级重量。页面展示的剩余量由后端全部记录汇总，不靠当前显示行数计算。
- 新增记录按种植周期、采收批次顺序加事务锁；不同请求并发也不能超分配或超包装。采收、分级及包装分别使用操作键和内容摘要识别重试，变更内容不能沿用同一确认；分级核对重复确认不重复改变状态。
- 生产人员只能办理本机构，只有管理员可跨机构；只读人员可查看但不能写入。接口与服务共用权限和校验，供后续 Agent 接入。
- 新采收仅允许进行中的种植周期，实际时间不能早于种植日期或晚于当前时间；分级不能早于采收，包装不能早于对应分级。
- 待分级核对的采收会阻止结束种植，结束日期不能早于实际采收日期。完成采收和分级核对后可以释放地块，历史批次继续包装，不因换季重新归属；尚未发生或尚未登记的采收仍需负责人核实。

## 升级与当前边界

新环境使用完整 `database/schema.sql`；已有环境完成前 3 批迁移后执行 `database/migrations/004_harvest_packing.sql`，仅新增 `harvest_lot`、`harvest_grade`、`packing_lot` 三张表。本次本地环境已应用迁移，没有重置或删除旧记录。

也可从仓库根目录使用已有 Java 11 与 MySQL JDBC 驱动；配置读取本地 `.env`：

```powershell
& '<Java 11目录>/bin/java.exe' '-Dfile.encoding=UTF-8' -cp '<mysql-connector-java.jar路径>' scripts/ApplyHarvestSchema.java
```

每周期显示最近最多 200 批采收，待核对优先；每批最多 200 条分级记录，包装展示最近 200 批，汇总仍覆盖全部包装。每个包装批次按同一单件净重登记，不同规格需分别登记批次。实际操作单当前不可编辑或删除；完整更正/冲销、附件上传、分级后的额外损耗、既有包装拆分或改装、混批、库存流水、销售、单品赋码与新业务上链尚未实现。需要更正时先停止后续办理并核对，不能通过再次采收补账掩盖差额。

包装保存只表示人工登记了实际包装，不自动记为入库、销售、赋码、已上链或实物质量合格。既有通用产品批次与新采收包装对象未自动映射，不能据此宣称消费者已能查询完整新来源。
